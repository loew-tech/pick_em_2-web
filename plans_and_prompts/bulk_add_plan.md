# Explore Category Page — Implementation Plan

Goal: add a dedicated explore page for one category that (1) lists all of its activities, (2) filters them by interest and effort, (3) deletes activities one at a time, and (4) bulk-adds activities via `POST /categories/{category_id}/activities/bulk`. Delivered in three gated phases; no phase starts without your approval of the previous one.

### 2. Proposed Architecture

Keep the new page inside the existing shape of the app: one new page component owning local state, the existing API client as the only network boundary, existing components reused, MUI + sibling SCSS for styling, and no new dependencies or global state.

**What is leveraged (no change):**

- Data for one category: reuse `getCategories([categoryId])` and take the first element (it already handles auth-header fetching and per-category fetch). This avoids changing `getCategory`'s caller-supplied-header signature and its existing tests. If that reads awkwardly in review, the fallback is a small new `getCategoryById(categoryId)` wrapper in the client that fetches its own auth header — noted as a review-time choice, not a prerequisite.
- Delete: reuse `removeActivity(activityId, activity)` as-is; an `Activity` from the list already satisfies its `ActivityData` parameter, and its `ClientArgumentError` / `API_Error` behavior is already tested.
- Display: reuse `ActivityCard` for name/interest/effort rendering and click-through to the existing edit page, and the `Tier` / `TIER_LABELS` model for filter values.
- Auth, loading, and error UX: copy the established page pattern (auth-check effect → redirect to `/login`, `LoadingSpinner`, `Alert` for error/success) so the new page behaves identically to Home and Activity pages.
- Bulk endpoint contract: implement exactly the documented flat body `{ activities: [{ name, interest, effort }] }` — no `category` or `activity_id` per item, since the category is in the path.

**What has to change:**

1. Routing — add exactly one route in [src/main.tsx](/C:/Users/steve/Documents/programming/ui/pick_em_web_2/src/main.tsx:15): `/categories/:categoryId/explore` rendering the new page (decided). It stays unambiguous next to the existing `/categories/:categoryId/activities/:activityId` route and does not claim `/categories/:categoryId` for this purpose.
2. Filter control — `FilterDropdown` only accepts a concrete `Tier`; there is no way to express "no filter". The page will hold `interestFilter: Tier | null` and `effortFilter: Tier | null` (`null` = All, the default) and filtering is a client-side `useMemo` threshold match over the fetched activities (both filters combine with AND): an activity is shown when `interestFilter === null || activity.interest >= interestFilter` and `effortFilter === null || activity.effort <= effortFilter`. That is, interest is “at least this interest” and effort is “at most this effort” (decided). With `Tier` values LOW=1, MEDIUM=2, HIGH=3 this means e.g. interest MEDIUM shows MEDIUM and HIGH, and effort MEDIUM shows LOW and MEDIUM. Smallest change: extend `FilterDropdown` with an optional `allowAll` prop that adds an "All" `MenuItem` and widens its value type to `Tier | "all"` at the component boundary, converting to/from `null` in the page. Existing callers (`ActivityForm`, `PickEmHomeContainer`) pass no `allowAll` and are unaffected. Rejected alternative: two explore-only dropdown components — duplicates an existing control for one extra menu item.
3. Delete affordance — `ActivityCard`'s whole surface is a `ButtonBase`, so a delete button cannot be nested inside it (invalid nested-interactive HTML and an accessibility problem). Smallest change: add an optional `onDelete?: (activity: Activity) => void` prop to `ActivityCard`; when present, render a small MUI delete `IconButton` (using `@mui/icons-material`, already a dependency) as a sibling positioned over the card corner, with `event.stopPropagation()` so it never triggers the edit navigation. When absent, the card renders exactly as today, so Home's inline explore lists are untouched until we choose to pass the prop there.
4. API client (Phase 3 only) — add one exported function following the existing client patterns, e.g. `bulkAddActivities(categoryId: string, activities: BulkAddActivityInput[]): Promise<void>`, where `BulkAddActivityInput = { name: string; interest: Tier; effort: Tier }` (equivalently `Omit<ActivityData, "category">`, declared once in [Activity.ts](/C:/Users/steve/Documents/programming/ui/pick_em_web_2/src/models/Activity.ts:15) or [types.ts](/C:/Users/steve/Documents/programming/ui/pick_em_web_2/src/common/types.ts:1) — implementer's pick, flagged in §5). It validates the category with the existing `isValidCategory` (throwing `ClientArgumentError(CATEGORY)` like `addActivity`), rejects an empty activities array with `ClientArgumentError` before any fetch, gets the auth header via the existing private helper, and `POST`s `JSON.stringify({ activities })` to `${API_URL}/categories/${encodeURIComponent(categoryId)}/activities/bulk` with `Authorization` + `Content-Type: application/json`. It returns nothing on success: the lambda's `201` body is only `{ "msg": ... }`, so there are no created objects to parse — resolving at all (i.e. `response.ok`) is the page's go-ahead signal. On any non-2xx it throws `API_Error`, exactly like the other client functions. Mirroring `addActivity`'s validation and error behavior keeps the client predictable; the flat request shape is the one deliberate difference, per the documented contract.
5. Bulk-add UI (Phase 3 only) — a page-local form section on the explore page. Recommended shape: dynamic rows, one row per new activity, each row a name `TextField` plus interest and effort `FilterDropdown`s (reused, without `allowAll`), an "Add row" button, a per-row remove button, and one Submit that sends all valid rows in a single bulk request. Submit is disabled when there are no rows or any row has an empty name; client-side validation mirrors the single-add rule (name required). Rejected alternatives: raw JSON textarea (fast to build, hostile to use, error-prone tier entry) and comma/line-based text parsing (ambiguous tier syntax — would need a documented mini-format invented by us). Row-based entry reuses existing controls and the `Tier` model directly. If you prefer a paste-many-names affordance, say so before Phase 3 — it changes this component's shape.
6. Home action buttons (Phase 1) — in [PickEmHomeActionsButtons.tsx](/C:/Users/steve/Documents/programming/ui/pick_em_web_2/src/components/homePage/PickEmHomeActionsButtons.tsx:41): rename the existing Explore button to "View activities", keeping its current behavior unchanged (fetch the checked categories via `getCategories` and render them inline on Home; disabled when no categories are selected, i.e. enabled when at least one category is selected). Add a new "Explore" button next to it that navigates to the single-category explore page for the one selected category: `navigate(\`/categories/${encodeURIComponent(selectedCategoriesIds[0])}/explore\`)` (path segment encoding matches the API client's convention; route decided as `/categories/:categoryId/explore`). No new props are needed — the component already receives `selectedCategoriesIds` and already uses `useNavigate`. Confirmed wording: this is *exactly one category selected* — the new Explore button is disabled whenever `selectedCategoriesIds.length !== 1` (zero or two-or-more selected) and enabled only when exactly one category is selected.

**Page state design (all phases):** the explore page owns `category: Category | null`, `loading`, `error`, `message`, the two filter states, a `deletingId` (to disable only the in-flight delete button), and (Phase 3) the bulk rows + `submitting` flag. Delete fires immediately with no confirmation (decided — same as the existing edit page). A successful delete (`HttpStatus.OK` from the lambda, surfaced by `removeActivity` resolving — its existing `!response.ok` check already throws `API_Error` for any non-OK status) removes the activity from local state; no refetch. Any other outcome keeps the item in the list and changes nothing except showing an error `Alert`. Bulk-add handling uses the `201` as a go-ahead only, to minimize AWS cost. On success (`bulkAddActivities` resolves), the page appends the just-submitted rows to `category.activities` locally — building each local `Activity` from the submitted `{ name, interest, effort }` plus `category: categoryId` — clears the rows, and shows a success `Alert`. No second API call is made after a bulk add: no `getCategories` / `getCategory` refetch. Because the `201` carries no created objects, these locally appended items have no server `activity_id`; the page assigns a temporary local identifier (e.g. `local-<n>`, used only as the React key and `activity_id` placeholder in page state). Accepted consequence of the cost decision: a just-added item is display-only in effect until the page is next loaded — opening it for edit or deleting it before then would call the API with the temporary id and fail with an alert; after a reload it returns with its real id and behaves normally. No attempt is made to hide this: it is the explicit trade for zero extra calls, and the rejected alternative was refetch-after-201. Server-side normalization (the lambda trims names) is likewise not reflected in the local copies until reload. Bulk-add failure (any non-`201`, thrown as `API_Error`) changes nothing in the collection and does not clear the entered rows; the only UI change is the error `Alert`. No optimistic insertion either: local state is updated only after the `201` go-ahead, never before the request resolves.

**Entry point (how a user reaches the page) — decided:** Home's action buttons in `PickEmHomeActionButtons`. The existing Explore button becomes "View activities" and keeps its multi-category inline behavior; a new Explore button beside it navigates to `/categories/{selectedCategoryId}/explore` and is disabled unless exactly one category is selected (`selectedCategoriesIds.length !== 1`). No title/link is added in `CategoriesActivitiesContainer`. This ships in Phase 1 together with the page, so the feature is discoverable as soon as the page exists.

**Testing strategy:**

- API client (Phase 3): extend [client.test.ts](/C:/Users/steve/Documents/programming/ui/pick_em_web_2/src/api/__tests__/client.test.ts:1) in its established style — exact URL/method/headers/flat JSON body assertion, category URL-encoding, resolves on a `201` (exactly one `fetch` call, response body not consumed as data), `ClientArgumentError` for an invalid category and for an empty array (asserting `fetch` was never called), `API_Error` on non-2xx, `AuthenticationError` propagation.

New `BulkAddForm` tests in Phase 3 (add/remove row, submit disabled states, submits the exact payload array).
- Page: new `src/pages/__tests__/explore.test.tsx` mocking `aws-amplify/auth`, `react-router-dom` params/navigation, and `../../api/client` exactly as [activity.test.tsx](/C:/Users/steve/Documents/programming/ui/pick_em_web_2/src/pages/__tests__/activity.test.tsx:1) does — covering auth redirect, loading spinner, list rendering, empty category, fetch failure alert, filter behavior (including All defaults and combined interest+effort), delete success/failure (Phase 2), and bulk submit success/failure (Phase 3: success appends the submitted activities locally and does not call `getCategories` again; failure leaves the list and rows untouched and only shows the error alert).

### 5. Risks and open questions

Decisions that materially affect the design — none of these will be silently decided:

1. **Route shape — resolved:** `/categories/:categoryId/explore`. The new Explore button on Home targets this path.
2. **Entry point — resolved:** rename the existing Home Explore button to "View activities" (behavior unchanged) and add a new Explore button beside it, disabled unless exactly one category is selected, navigating to that category's explore page (see §2, change 6). The criterion's "one activity selected" wording is confirmed to mean *exactly one category selected*.
3. **Delete confirmation — resolved:** fire immediately, as the existing edit page does; no confirmation dialog. `HttpStatus.OK` (a resolved `removeActivity` call) is the signal to remove the item from the UI; otherwise the item stays and only an error message updates.
4. **Bulk-add input format:** dynamic rows (recommended — reuses `FilterDropdown`, tiers can't be mistyped) vs paste-oriented input (textarea of names with shared tier settings, or one-name-per-line). This is the biggest open product decision; it changes `BulkAddForm`'s shape entirely, so it must be settled before Phase 3 starts.
5. **Bulk response semantics — resolved:** the lambda returns `201` with only `{ "msg": ... }`. That `201` is the go-ahead to append the submitted activities locally; no refetch is made (cost decision, explicitly rejecting refetch-after-201). Any non-`201` only produces an error alert. Partial success cannot occur — the lambda validates every item before writing any — so no per-item result display is needed. Known accepted limitation: locally appended items carry temporary `local-<n>` ids until the next page load, so edit/delete on a just-added item before then will fail against the API; this is the documented price of zero extra calls, not an oversight.
6. **Bulk limits and validation (largely observed):** the lambda requires a non-empty list and a non-empty (trimmed) name per item, and valid tier values; no maximum count and no duplicate-name check were found in the handler. The plan validates non-empty names client-side (mirroring single-add) and otherwise relies on the `400` → error-alert path.
7. **Filter semantics — resolved:** threshold semantics with an "All" default: interest is “at least this interest” (`activity.interest >= selected`) and effort is “at most this effort” (`activity.effort <= selected`); `All` disables that dimension. Both combine with AND. This differs from `getPick`'s exact-tier selection and is intentional for browsing.

Technical risks (lower-order, with mitigations already in the plan):

- `FilterDropdown` widening: adding `allowAll` touches a component used by `ActivityForm` and Home. Mitigated by making it opt-in and running the full suite, not just new tests.
- `ActivityCard` restructure: moving the delete button outside the `ButtonBase` must not break the card's click/hover/focus behavior or its existing class-based tests. Mitigated by rendering the button only when `onDelete` is passed and adding explicit no-navigation tests.
- `getCategories([categoryId])` returns an array for a single-category need — slightly indirect, and a nonexistent category surfaces as an `API_Error` from the underlying fetch, which the page shows as a generic failure rather than a "category not found" state. Acceptable for Phase 1; a dedicated single-category client helper can be added later without UI changes.
- List size: a category with very many activities renders all cards at once (same as today's inline explore). No virtualization is proposed; if real categories are huge, that is a follow-up, not Phase 1 scope.
